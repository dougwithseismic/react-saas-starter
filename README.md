# React SaaS Starter

## Deploy on Railway

[![Deploy on Railway](https://railway.com/button.svg)](https://railway.com/deploy/saas-starter-with-react-hono-and-better-auth--saas-starter-with-react-hono-and-better-?referralCode=dougie)

The template creates Postgres, the API and the web proxy on one private network. Only the web proxy is public, so the app and API share one HTTPS origin. It generates the auth secret for each deploy, runs migrations before each API deploy and needs no input. Email, analytics and billing stay off until you add the Loops, PostHog and Stripe variables. `deploy/RAILWAY.md` lists every service setting and variable. The button uses my Railway referral code.

```text

Apply [DESIGN REFERENCE] to the React frontend while preserving the account and organisation flows. Deploy to [HOSTING PROVIDER] at [DOMAIN]. Work through the checklist below, run the database and browser tests, and verify the live account flows. Keep credentials server-side, report missing provider access or configuration, and distinguish tested integrations from live delivery. Keep the scope to accounts, organisations and billing unless I specify product features.
```

## Setup checklist

1. **Create the application repository.** Use the public GitHub template to create a private repository: `gh repo create my-app --private --template dougwithseismic/react-saas-starter --clone`. Open the new folder and read `AGENTS.md`.
2. **Install the local tools and dependencies.** Use Node.js 24+, the pnpm version pinned in `package.json`, and Docker Compose. Run `corepack enable` and `pnpm install`.
3. **Set the application identity and local configuration.** Replace the starter name and branding. Copy `apps/server/.env.example` and `apps/web/.env.example` to `.env` files in their respective folders. Generate `BETTER_AUTH_SECRET` with `openssl rand -base64 48`. Set `DATABASE_URL`; keep `APP_ORIGIN` and `BETTER_AUTH_URL` at `http://localhost:4300`. The web app uses port 4300, Hono 4301, and local PostgreSQL 5433. Keep secrets out of Git.
4. **Start and migrate PostgreSQL.** Run `docker compose up -d --wait`, then `DATABASE_URL=postgresql://starter:starter@localhost:5433/starter pnpm db:migrate`. Use a separate disposable database for integration tests and migrate it too. Keep schema changes and reviewed migrations in `packages/db`.
5. **Configure Loops email.** Verify the sending domain and publish three transactional templates. Set `LOOPS_API_KEY`, `LOOPS_RESET_PASSWORD_TEMPLATE_ID`, `LOOPS_VERIFY_EMAIL_TEMPLATE_ID` and `LOOPS_INVITATION_TEMPLATE_ID` on the server. Every template needs `url` and `name`; invitations also need `organizationName`, with `name` representing the inviter. The verification template also handles email changes. Account emails do not enroll recipients in a marketing audience. Without configuration, recovery and verification cannot deliver email; manual invitation links still require a verified recipient.
6. **Configure analytics.** Set server `POSTHOG_PROJECT_KEY` and `POSTHOG_HOST`, plus browser `VITE_POSTHOG_PROJECT_KEY` and `VITE_POSTHOG_HOST`, using the same project and its ingestion host. Browser keys must be public project keys. Browser values require a rebuild; unset keys disable analytics. For another provider, replace the sinks in `apps/web/src/lib/analytics.ts` and `apps/server/src/modules/analytics/analytics.ts` without changing feature code. Verify client and server events, user identification and logout reset.
7. **Configure Stripe billing.** Organisations subscribe to the plans in `packages/contracts/src/billing.ts` (Free, Pro and Team as an example); edit their names, labels and entitlements there. Work in Stripe test mode. Create a recurring price for each paid plan and set `STRIPE_PRICE_PRO` and `STRIPE_PRICE_TEAM`; to change a price later, list the new id first and keep the old one after a comma so its subscribers stay on the plan. Set `STRIPE_SECRET_KEY` to the test secret key (or a restricted key that can write customers, Checkout Sessions and portal sessions and read invoices). Install the Stripe CLI, run `stripe listen --forward-to localhost:4301/api/billing/webhook` and set `STRIPE_WEBHOOK_SECRET` to the `whsec_` secret it prints. In the dashboard's Customer Portal settings, allow payment method updates, cancellation and switching between the paid prices. Restart the server, open an organisation's billing page, subscribe with a [test card](https://docs.stripe.com/testing) and check the plan turns active. Billing stays off, and the page says so, until both keys are set. The webhook handles `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid` and `invoice.payment_failed`; give a hosted endpoint exactly those events and API version `2026-10-28.endive`, the one the server's Stripe SDK uses. Server code reads an organisation's plan with `billing.entitlements(organizationId)`, and paid invoices reach the `invoicePaid` listeners passed to `createBilling` in `apps/server/src/index.ts` (see `apps/server/src/modules/billing/hooks.ts`).
8. **Connect logging and monitoring.** Set `LOG_LEVEL` and connect the server's Pino JSON output to your hosting log service. Confirm request IDs, method, path, status and duration are visible. Keep credentials, request bodies and query strings out of logs. Monitor `/health/ready` and application failures.
9. **Apply the frontend design.** Update tokens and primitives in `packages/ui`, then layouts and screens in `apps/web/src`. Keep TanStack Query for remote data, TanStack Router for navigable state, and Zustand for UI preferences. Better Auth owns authentication; Hono enforces API access. Put new server modules in `apps/server/src/modules` and shared DTOs in `packages/contracts`.
10. **Check local account flows.** Run `pnpm dev` and open `http://localhost:4300/sign-in`. The login API is `POST /api/auth/sign-in/email`; Scalar is at `/docs` and the API specification at `/openapi.json`. Check signup, login, logout, profile updates, email verification/change, password recovery/change, session revocation and account deletion. Check organisation creation/editing/deletion, member roles, invitations and protection of the final owner. Check billing as an owner and as a member.
11. **Run the automated checks.** Run `pnpm verify`, install browsers with `pnpm --filter @repo/web exec playwright install chromium webkit`, then run `pnpm test:e2e`. Set `TEST_DATABASE_URL` to the migrated disposable database to include persistence and permission tests. Confirm GitHub Actions can run; account billing or spending limits can block jobs before they start.
12. **Configure production hosting.** For Railway, follow `deploy/RAILWAY.md`. Otherwise, provision the domain, PostgreSQL and application host. Copy `deploy/.env.example` to `deploy/.env` and supply the production domain, database credentials, auth secret, Loops settings, analytics settings and Stripe settings. Add a Stripe webhook endpoint at `https://<domain>/api/billing/webhook` and use its signing secret. Keep the frontend and API on the same HTTPS origin through Caddy or an equivalent reverse proxy. Preserve the SPA fallback, run migrations before starting the API, and allow only verified proxy socket IPs or private CIDR ranges in `TRUSTED_PROXY_IPS`. Keep the database private and configure backups.
13. **Build and deploy.** Validate the configuration with `docker compose --env-file deploy/.env -f deploy/compose.yaml config`, then build and start it with `docker compose --env-file deploy/.env -f deploy/compose.yaml up --build -d`, or use your host's equivalent pipeline. Point DNS at the host and verify HTTPS. Validate the Docker templates on the deployment host; a successful local Node/Vite build does not prove container deployment. Changing browser analytics settings requires rebuilding the web image.
14. **Verify the live application.** Check `/health/ready`, `/docs`, direct account/invitation URLs and cookie persistence. Repeat the account and organisation flows with real test users, confirm Loops email arrival and usable links, confirm PostHog events and identity reset, complete a test-mode subscription and see it in the webhook's delivery log, and confirm logs and alerts. Test database restore and the release rollback process before relying on the application.
